Aster is an open-source hyperparameter optimization library for noisy simulations. It combines adaptive replication, a recoverable Python runtime, C++20 accounting, and resident CUDA training. The test case: neural hedging with transaction costs.

From allocation to execution

A small core, with performance work at each layer.

Adaptive simulation budgets
Full-budget search, stopping ASHA, and replication racing share a typed candidate pool. Paired outcomes guide which candidates receive more simulation work.
Recoverable experiments
A coordinator owns the SQLite journal. Seed-preserving retries, resume, attempt and wall-time limits, evaluation timeouts, and cancellation make interrupted runs inspectable.
Independent winner audits
Lock the selected configuration, then evaluate it with fresh audit seeds. Training, shared market scenarios, and audit randomness use separate namespaces.
C++20 accounting
An optional native companion computes hedge P&L, transaction costs, and turnover. It offers batch operations, caller-owned output buffers, and a streaming ledger.
Resident CUDA execution
Simulation, neural training, and evaluation share float64 GPU arrays. Fused kernels reduce launch overhead; small supported batches use four training kernels per epoch.
Reusable managed workers
One owned process pool can serve successive searches and audits, retaining healthy worker contexts and caches. Repeated-run performance is still pending.

What is timed

Backend setup, numerical imports, host random inputs, transfers, simulation, training, evaluation, scheduling, SQLite journals, winner selection, audits, and result writes. Each campaign starts in a fresh process with the ordinary shared compiler cache already populated by validation.

Where CPU still wins

Four CPU workers are faster on the small workload. Including interpreter startup and exit gives 1.165 s for small optimized CUDA versus 1.124 s for one CPU worker: roughly parity. NumPy remains the default backend.

Kernel changes, correctness, and timing limits

Nsight recorded 10,985 → 361 kernel executions for the small diagnostic and 11,126 → 5,174 for the larger one. Small supported batches fuse forward evaluation, accounting/error, gradients/loss, and Adam into four training launches per epoch. Larger batches keep CuPy/cuBLAS gradients and use the fused optimizer.

The larger diagnostic's summed GPU kernel duration increased 6.8%, even as host time fell. The unprofiled workflow comparison establishes the reported speedup; fewer launches do not imply faster arithmetic in every kernel.

Across 594 accepted search evaluations and 126 audits, no objective failed. All seven matched financial metrics passed rtol=1e-6, atol=1e-8; reported winner/allocation pairs agreed. Three seeds on one A100 provide descriptive engineering evidence, without a tail-latency or broad financial quality guarantee.

Including interpreter startup and exit, larger median process times are 16.809 s (CPU / 1), 8.970 s (CPU / 4), and 3.874 s (optimized CUDA). Paired process speedups are 4.34× and 2.41×, respectively. These differ from the workflow headline numbers.

One optimizer, optional numerical backends

Own the experiment. Keep the hot path close to the data.

The dependency-free Python core controls allocation, execution, and recorded state. Numerical work lives behind the objective interface; optional native and GPU components extend the financial workload.

Statistical boundaries

ReplicationRace uses paired outcomes and a standard-error margin to prune candidates. Repeated inspection and adaptive peer selection make it a heuristic, without a formal confidence-sequence guarantee. Audit statistics are descriptive. Separate noise diagnostics include cases where racing prunes a true optimum.

Runtime ownership and current limits

The coordinator owns journal writes and rejects stale or duplicate responses. Retries keep the same simulation seeds; committed observations survive resume. Cancellation and timeouts reap owned workers with bounded cleanup. A worker pool fixes capacity and thread limits, and leases workers to one invocation at a time.

Unbounded one-worker calls already run in the caller and retain CUDA caches within that interpreter. WorkerPool adds managed process isolation and reuse. Models, random paths, and optimizer state are recreated for every hedging evaluation.

The current system targets one host and one GPU for CUDA objective execution. Distributed scheduling, multi-GPU execution, and cross-framework end-to-end performance comparisons remain future work.

Start with the CPU reference

Run a financial simulation locally.

From a source checkout containing the 0.3 runtime, use Python 3.11+ and install the optional numerical and reporting tools below. The core has no runtime dependencies. Use a fresh output directory for each run.

Source checkout · macOS / Linux 
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[benchmark]'
python -m examples.hedging --workers 2 --configs 4 \
  --output results/hedging-first

This is a pilot, not a reproduction of either frozen comparative study. The linked reports provide their exact protocols, versions, source revisions, and reproduction commands. This website serves saved evidence; visiting it does not start a computation.

Run the CUDA backend on an NVIDIA development host

With a working CUDA 13 environment, install the matching optional backend and use one objective worker per GPU: 

python -m pip install -e '.[benchmark,cuda13]'
python -m examples.hedging --backend cuda --workers 1 \
  --configs 4 --batch-paths 4096 --evaluation-paths 32768 \
  --output results/hedging-cuda-first

The A100 study used CUDA 13.2 and CuPy 14.2.0. CUDA selection is explicit; an unavailable device raises an error. Inspect the measured setup ↗

Build the optional C++20 companion

With a C++20 compiler and CMake installed, build the separate Python companion from the source checkout: 

python -m pip install ./native

The NumPy reference used in the tables above is the CPU baseline. Those tables do not claim that every CPU objective uses the C++ companion.

Persistent GPU workers

The WorkerPool API is implemented and correctness checks have exercised worker reuse, changed inputs, cancellation, and recovery. The comparative performance study has not run; no repeated-run CPU/CUDA speedup is claimed.

The prepared protocol compares direct calls, fresh pools, and reused pools for CPU and CUDA, including four-worker CPU controls. It separates first-run latency, later runs, and whole-sequence cost including shutdown. Models and optimizer state start fresh for every evaluation.
